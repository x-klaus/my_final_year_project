ATBU Smart Transport System — Backend Handoff Guide

Project: Final-year frontend prototype
Stack: Static HTML + CSS + vanilla JavaScript (no build step)
Entry script: js/app.js (loads all modules in order)
Demo persistence: localStorage / sessionStorage (replace with REST API + DB)

1. Purpose of this document

This guide helps the backend engineer integrate APIs without redesigning the UI. The frontend is complete for demonstration; all business logic that should live on the server is currently simulated in the browser.

Verdict: UI is ready for handoff. Backend must implement authentication, persistence, payments, real-time fleet data, and QR verification.

2. How to run the prototype

  1. Open the project folder in VS Code (or any static server).
  2. Use Live Server or similar: serve from project root (e.g. http://127.0.0.1:5501/).
  3. Start pages:
  4. Public: index.html
  5. Student/Driver login: login.html
  6. Admin login: admin-login.html (not linked from public site)

Script load order (via js/app.js):

js/core/utils.js → auth.js → public.js → auth/login.js → auth/register.js
→ student/dashboard.js → student/tracking.js → student/booking.js
→ driver/driver.js → admin/admin.js → core/bootstrap.js

4. Authentication (replace first)

4.1 Current behaviour (prototype)

  • Session stored in sessionStorage key atbuAuthSession.
  • Shape: { role, name, email, reg, loggedInAt }.
  • No password verification — any valid-looking input logs the user in after a short delay.
  • Guards: requireAuth() in js/core/auth.js reads data-auth-role on <body> and redirects if missing/wrong role.

4.2 Suggested API contract

Action Suggested endpoint Notes
Student login POST /api/auth/login body: identifier + password
Driver login POST /api/auth/driver/login or same endpoint with role
Admin login POST /api/auth/admin/login separate; accounts provisioned by IT
Register student POST /api/auth/register/student
Register driver POST /api/auth/register/driver
Logout POST /api/auth/logout clear cookie/token
Session GET /api/auth/me return profile for guards

Frontend changes: Replace getAuthSession / setAuthSession in js/core/auth.js with token/cookie handling; keep the same redirect URLs (getDashboardUrlForRole, getLoginUrlForRole).

4.3 Admin accounts

  • No self-registration in the UI. Admins use admin-login.html only.
  • Backend should provision admin users; share the admin URL out-of-band.

8. Key user flows (backend must support)

8.1 Student wallet (top-up & activity)

  1. student-wallet.html — balance card, inline top-up (preset/custom amounts), Paystack/Flutterwave radios (UI only).
  2. Top-up: processTopUp() → credit balance + recordWalletTopUp() → renderWalletTransactions().
  3. Activity table: reads walletTransactions (not booking history). Types: Credit / Debit.
  4. Dashboard shortcut: wallet card links to student-wallet.html / #topup / #history (scroll to activity).

Functions: initStudentWalletPage(), renderWalletTransactions(), addWalletTransaction().

8.2 Student books a seat

  1. Select route → bus → seat → payment (booking.html).
  2. Wallet path: deduct BOOKING_FARE, recordWalletBookingDebit(), set hasActiveBooking + activeTicket.
  3. Paystack/Flutterwave buttons are UI only — integrate real payment webhooks.
  4. 15-minute boarding timer (boardingExpiryTime) — expire booking + refund if not boarded.

Functions: processBookingPayment(), handleBoardingTimerExpired() (refund + recordWalletRefund), executeCancelBooking(), archiveBooking().

8.3 Driver boards passenger

  1. driver-scan.html or manifest → enter/scan ref.
  2. markPassengerBoarded(ref) → append to driverBoardedRefs.
  3. Updates stats, manifest, student ticket UI.

API: POST /api/driver/verify-boarding with { ref }.

8.4 Driver trip lifecycle

  1. Idle → Start trip (moving) → optional At stop (stopped) → End trip.
  2. End trip may credit earnings and call completeTripForStudents() → moves active booking to history.

API: Trip state machine on server; WebSocket optional for admin/student live updates.

8.5 Admin views

  • Fleet rows from busData + driver state for BUS-002.
  • Bookings table from getAllAdminBookingRows() — merges history + active ticket.
  • Listens to storage events today; replace with polling or WebSocket.

13. Recommended integration order

  1. Auth (student, driver, admin) + protect routes
  2. Student profile + wallet balance + transaction ledger + create/cancel booking
  3. Driver trip state + boarding verification
  4. Admin fleet + bookings read APIs
  5. Payments (Paystack/Flutterwave)
  6. Real-time (WebSocket/SSE) for map and admin
  7. Collective bus requests + admin fleet management (if in scope)

14. Contact / frontend notes

  • No npm build — drop-in API client functions can live in js/core/api.js (suggested).
  • CORS: Frontend expects to be served from same origin as API or configured CORS.
  • js/main.js: Deprecated shim; all pages use js/app.js.
  • Page init must run from bootstrap.js after all modules load (cross-file dependencies). Page hooks use element IDs (e.g. studentWalletPage, driverScanPage).
  • student-wallet.html layout: CSS grid — desktop balance + activity top row; top-up card left column only; mobile stacks balance → top-up → activity.
  • Clear booking history (student history page) also clears walletTransactions in the prototype.
